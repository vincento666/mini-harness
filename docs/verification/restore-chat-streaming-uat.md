### `>>` 的根因（已验证，非本 change 引入）

- `> ` 只有一处写入：`cli/main.py:786` 的输入循环顶部，且**不带换行**（design D1）。空白输入在 792–795 行 `continue`，回到循环顶部**再打一次** `> `；两个提示符之间没有我们写的换行，管道里就是 `> > `（3 个 `> `，末两个连续）。
- 真端点对照（同一提示词，`--max-steps 1 --yes`，管道）：

  | 场景 | stdout 末尾 `> ` 数 | 末尾形态 |
  |---|---|---|
  | `--stream` + 提示词一行 + EOF | 2 | `…正文\n> `（正常：行首 + 轮后） |
  | `--stream` + 提示词 + **空行** + EOF | **3** | `…正文\n> > ` |
  | `--no-stream` + 提示词一行 + EOF | 2 | `…正文\n> ` |
  | `--no-stream` + 提示词 + **空行** + EOF | **3** | `…正文\n> > ` |

- pty 复现（真 tty）：轮后是 `\r\n> `，多按一次回车（空行）后是 `\r\n> `——**相邻两行各一个 `> `**；终端回显把两者分行，人眼连着看容易读成 `>>`。整场 `'> '` 计数 3、字面 `'>>'` 计数 0。
- 结论：**`--no-stream` 同样出现 → 既有 REPL 行为，不是 `restore-chat-streaming` 引入**。按人裁「不扩本 change 范围」，不动公共循环（改它会动到 `--no-stream` 基线，违反契约 2.3「逐点相同」），记为 `docs/CURRENT.md` 开放缺口的独立缺陷；若要修（空白输入不重打提示符 / 补「一条输入只一个提示符」判据），另开 change。

### 根因归类（与场次 1 同源，非本 change 引入）

1. **决定性**：模型把内容放进工具调用 / 工具参数而不是正文，正文为空或纯换行——与场次 1 原判据不通过同源（工具参数增量不进正文 sink）。
2. **驱动语义**：模型在 s1 连发 2 次 `ask_user`（把「多轮」理解成「先问清楚」），目标轮 s2 一条 `bash` 被人 DENIED → `FENCE_DENIED` ∈ `NO_CONTINUE_REASONS` → 停止自动推进。这是 `goal-round-pacing` 的既定设计，不是本 change 能力。
3. **观感**：提问面板、审批面板、REPL 提示符在 stderr/stdout 交错，多处 `> `；与场次 1 复跑见到的 `>>` 属同一类既有交互问题。

## 场次 1 原判据实测与诊断（2026-11-25，人跑，不通过）

### 人跑事实（来自会话日志，已验证）

- 会话 `sessions/82db8aadc7b2421c80bd2168f7f42492.jsonl`，`entry=chat`、`prompt=生成1000字散文`、`max_steps=4`、`approval=ask`、`window=128000`、模型 `qwen/qwen3.8-27b`。
- **推断**：日志不记 `stream` flag；按 UAT 手册场次 1「不传 flag」的口径，这场应为默认 `--stream`。但下面的结论不依赖这个推断——`content` 为空时，流式与非流式都不会有正文可显示。
- 四条 `model/response` 的 `content` 分别是 `"\n\n"`、`""`、`""`、`""`（长度 2/0/0/0）；散文 1324 / 1343 / 386 / 344 字符全在 `tool_calls[0].arguments.command` 里（`bash` heredoc 写 `/tmp/essay.txt` 并反复改字数）。四步 `stop_reason` 依次 `TOOL_CALLS`×3、`MAX_STEPS`。
- 第 1 步 `model/request` 08:38:09.877 → `model/response` 08:38:52.493 = **42.6 秒**，期间 stdout 没有任何正文；`tool/call` 落在 08:38:52.495（响应后 2 ms），`_tool_observer()` 把整条命令 `json.dumps` 一次性打到 stderr（`cli/main.py:497-503`）。工作区根的 `essay.txt`（3464 字节，16:39）是这场之后取回的产物。

### 根因（三层，按影响排序）

1. **决定性**：模型把长文本放进**工具调用参数**而不是正文。`provider/openai_compat.py:307-322` 的 `_stream_tool_calls` 明写「参数片段只拼装，不交给正文 sink」；`_stream_generate` 只在 `delta.content` 非空时 `await on_delta(text)`（508–513 行）。CLI 侧 `_ChatStreamRenderer` 对纯空白增量只写不打标记（`cli/main.py:568-581`），`on_step_end` 因 `content.strip()` 为空不回退（583–593），`_print_new_replies` 同样跳过空正文（541–544）。所以**正文 sink 全程没有内容可显示**，`--stream` 开不开结果一样。
2. **观感**：工具参数增量没有任何呈现，`[tool] bash {...}` 在整条流结束后一次性打全文（含 1000 字散文），看起来就像「攒到最后一次性输出」。
3. **体感**：`qwen/qwen3.8-27b` 是 thinking 模型。裸 curl SSE 实测（同一端点、`stream:true`、约 200 字散文提示）：575 个 chunk 里 **547 个带 `reasoning` / `reasoning_details`**，前 1–10 秒 `delta.content` 一直是空串；当前 main 的 provider 只取 `content`、忽略 reasoning，所以这段时间屏幕上完全空白。这与 `docs/reference/h2-streaming-and-reasoning.md` §6.1 的状态注记一致：**思考帧已在 `origin/change/reasoning-mode-and-budget` 与 `origin/change/chat-streaming-shell` 两条分支实现，但都没合入 main**；是「已实现未合入」，**不是 deferred**（2026-11-25 纠正）。

### 不是实现回归（真端点诊断实验，非 tty 手感验收）

为把「流式链路本身是否正常」从推断变成读数，用真端点跑了三场管道实验（`os.read` 直接读 fd，按秒分桶统计 stdout 字节；`--max-steps 1 --yes`，非 tty，不替代 ADR-0025 的人眼手感）：

| 场 | 提示词 / flag | stdout 到达 | 结论 |
|---|---|---|---|
| A | 「不要用任何工具…直接写约 300 字散文」/ 默认 | 首字节 0.28s 是提示符 `> `；正文首帧 **11.36s**，之后 11–12s 多次小 read（9/6/21/3/9/27…字节），共 848 字节 | 正文增量**陆续到达** |
| C | 同一提示词 / `--no-stream` | 正文在 **8.99s 一次性 1104 字节** | 攒批对照成立 |
| B | 「生成1000字散文」/ 默认 | 正文 3280 字节分多次 read 在 **10.16–11.4s** 到达 | 流式正常；这场模型把散文写在**正文**里，与用户那场不同，说明「用工具还是用正文」有随机性 |

→ **已验证**：默认 `--stream` 生效、正文增量实时到达，`--no-stream` 确实回到一次性；`restore-chat-streaming` 的正文流式实现没有回归。
→ **推断到已验证的边界**：以上只证明「正文有内容时」的链路；「工具参数增量」与「reasoning 增量」不在本 change 的 sink 契约内。前者是尚缺的新能力，后者已在未合入分支实现，两者性质不同。

### 结论与人裁

- 原判据「提一个需要长回答的问题 → 正文逐段出现」在这台模型 + 这句提示词下**不可达**：模型用工具承载长文本，正文为空。
- **人裁（2026-11-25，选「修判据并归档」）**：修订判据而非扩大范围。场次 1 提示词改为明确「不要用任何工具、直接写在正文里」（见「跑之前的准备」），复跑已通过；三个缺口都不并入本 change，但**性质不同**：思考帧是「已实现未合入 main」（合入/迁移），工具参数增量的终端呈现与空白输入重复提示符是另开 change / 独立缺陷，分别记入 `docs/CURRENT.md` 开放缺口。**原不通过事实保留在本节，不因判据修订而抹掉。**

**场次 1（修订判据）的输入**（直接粘到提示符；关键是明确禁用工具，否则模型可能把长文本放进 `bash` heredoc，正文为空、判据不可达）：

```
不要用任何工具，不要写文件，不要调用 bash 或其他工具，直接在回复正文里写一段约 600 字的散文，题目自拟。
```

观察：正文是否逐段滚出、`[answer] ` 是否恰一次、轮末是否没有整段重复。注意这台模型是 thinking 模型，正文首帧前可能有约 10 秒 reasoning 空白——`[thinking]` 已在未合入的 `chat-streaming-shell` 分支实现，当前 main 没有；把那条分支合入后这段空白会由思考帧填上，属于合入/迁移工作，不算本场判据失败。**粘贴后不要再多按一次回车**：多出的空行会让输入循环重打一个 `> `，末尾看起来像 `>>`（既有行为，见上）。

**场次 3 的命令**（注意 `--yes`：绕开审批面板与 `FENCE_DENIED`，否则一条被 DENIED 的 `bash` 就会终止目标自动续跑）：

```bash
uv run minihns chat --provider openrouter --proxy http://127.0.0.1:7897 --workspace .tmp/uat-scene3 --max-steps 4 --yes
```

**场次 3 的输入**（这段已由 agent 用真端点管道诊断验证能跑出 3 轮、每轮成段正文，会话 `7753dea6…`；直接粘到提示符）：

```
创建一个目标：分三轮给我讲一个完整的小故事，每一轮写一段。严格照做：1) 第一步用 create_goal 建目标，max_rounds 设为 3；建目标的本轮不要写任何正文、不要写第一段，只记一条 todo 计划就结束本轮；2) 之后每个目标轮都直接在回复正文里写出本轮那一段故事（约 80 字），不要写文件、不要调用 bash、不要把故事放进任何工具参数里，写完正文后用 todo 工具记一句本轮进度；3) 不要调用 ask_user、不要问我任何问题；4) 三轮都写完后用 update_goal 标 complete。现在开始。
```

观察：三段故事是否**各自成行不粘连**（每轮一段、不挤在一行）、`[轮] 1/3` 是否在第 1 段正文之前、`[轮] 2/3` 是否在第 2 段之前、`[轮] 3/3` 是否在第 3 段之前、一条输入是否只出现一次提示符。提示词里「建目标的本轮不要写正文」这句（change `round-label-prompt-alignment`，2026-11-26 人裁）保证模型不把第一段提前写进人类轮——否则 `[轮] n/cap` 按自动目标轮计数、n 与模型自述的「第 N 段」会错位（见下「场次 3 tty 人跑」节）。每轮都写了 `todo`，所以不会撞停滞闸门。`--yes` 下没有审批面板，提示词禁了 `ask_user`，所以屏幕不会再被面板打乱（这三个是**跑法隔离**，不是实现改动）。提示词里的故事是示例，可以换题目，但五条约束别删——删了模型可能又用工具承载正文、把第一段塞进人类轮、或停下来问问题，判据场景就不可达。

场次 4 的提示词建议：「分三轮讲一个故事，每轮一段，写完一段就停」。看到正文滚出来几个字后按 Ctrl-C。注意这条提示词**不建 goal**：三个轮全是人类轮，每段讲完会停下等「继续」——这是预期（自动连续多轮只在目标轮有），不影响本场判据（判据只看 Ctrl-C 的半句保留与收尾行）。
