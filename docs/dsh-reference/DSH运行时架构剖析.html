全景：一句话本质与整体分层

宏观
DSH 的本质是一台"可重新装配的 agent 运行时"。它不是一个写死的 agent 程序，而是一个 Cordis 依赖注入容器 + 91 个可替换服务 + 一份 YAML 组合清单。你看到的每一个功能——工具、沙箱、压缩、子代理、UI 面板——都是一个独立 npm 包，通过 cordis.patch.yml 声明式地插进容器里。官方口号 "Everything is a Plugin" 不是修辞，而是包结构事实：289 个 @deepseek-ai/* 包，全部是 Cordis 插件。
专业表述

DSH 采用 三层进程模型：Electron 外壳（@deepseek-ai/dsh-desktop）只负责窗口、自定义协议 dsh-app://、鉴权反代与更新；真正的 agent 运行时是一个 Node 模式宿主进程（@deepseek-ai/dsh-desktop-runtime，通过 ELECTRON_RUN_AS_NODE=1 启动）；原生能力由 app.asar.unpacked 里的 payload 提供。

宿主内部是 Cordis 的 Service / plugin / fiber 模型：插件声明依赖，框架做拓扑排序与生命周期编排，服务通过 ctx.<key> 暴露，跨层通信全部走 事件（waterfall / emit） 与 类型化 Remote RPC。

大白话

把它想成一台带插槽的电脑：主板（Cordis 容器）提供电源和总线，CPU（agent 主循环）负责思考，显卡/网卡/硬盘（工具、沙箱、会话、模型适配）都是插卡。想换功能不用改代码，换插卡就行——而"插哪张卡、插什么顺序、哪张卡禁用"写在一份 YAML 清单里。

Electron 外壳只是机箱和显示器：它自己不思考，只负责把画面显示出来、把外面的人挡在门外。

读这张图的三个要点

  1. 边界 A→B 是进程级隔离，不是函数调用。外壳用 ELECTRON_RUN_AS_NODE=1 把 Electron 二进制当 Node 用，spawn 出宿主；两者之间只有 process.send 词汇表（ready{port}、fatal、quit-inspection、update-tasks）。宿主崩了外壳能重启，外壳崩了宿主不受影响。
  2. 边界 B 内部没有"模块调用链"，只有服务与事件。包之间不 import 彼此的实现，而是 ctx.<service> 取服务、ctx.on/emit/waterfall 通信。这是它能被重新装配的前提。
  3. 边界 C 全靠运行时 FFI，静态导入分析看不到。Windows 沙箱的 17 个 advapi32 + 28 个 kernel32 函数全部由 koffi 在运行时绑定，PE 导入表里一个都没有。

工件层：一个 asar 里装着两个应用

宏观 · 取证

分析任何软件的第一步是搞清楚"你手上拿的是什么"。DSH 的 Windows 安装包 244,481,512 B，其中 resources/app.asar 是 121,348,951 B 的归档。这个归档不是单个应用，而是两个应用的嵌套。

专业表述

asar 归档头部布局：uint32@0 = 4（块大小）、uint32@4 = headerSize、uint32@8 = headerSize-4、uint32@12 = jsonSize，JSON 索引从文件偏移 16 开始，payload 基址 = 8 + headerSize。

根索引顶层键为 dsh、node_modules、lib、package.json、renderer。根 package.json 的 main: "lib/main.js" 决定 Electron 加载的是外壳，宿主只是被当作数据资源携带、由外壳 spawn。

大白话

asar 就是一个"带目录的 tar"。目录写在文件开头，正文跟在后面。算错正文起点 8 个字节，解出来的每个文件都会整体错位——本次分析早期就犯过这个错，导致出厂 manifest 看起来是坏的，一度误判成工件被篡改。

两个应用的关系像商场和里面的店铺：商场（外壳）管大门、保安、水电表；店铺（宿主）才是真正做生意的。店铺自己还带了一套货架（自己的 node_modules），不借用商场的。

为什么这个发现重要

它直接决定了"逆向 DSH"要问的是哪个问题。外壳层是安全边界（协议、鉴权、窗口权限），宿主层是语义边界（agent 行为、工具、沙箱）。混淆这两层会得出完全错误的结论——本次分析早期就因此误判过"DSH 没有任何 exposeInMainWorld"，实际上外壳里有 11 个。

组合层：Cordis 容器与 YAML 装配清单

核心 · 架构基石

DSH 建立在 cordis 4.0.4（+ cosmokit、schemastery）之上。这一层决定了其它所有层的连接方式：包之间不互相 import，只通过服务与事件对话。

专业表述

Cordis 是依赖注入 + 插件生命周期框架。插件声明它 inject 哪些服务（可用性 + 每服务的 intercept 配置）、intercept 哪些既有服务、provide 哪些新服务；框架按服务可用性驱动激活、按 fiber 层级编排 apply 阶段、按 registry 顺序处理事件、按 dispose 层级逆序析构。服务通过 ctx.<key> 访问，跨包通信走 ctx.on / emit / parallel / serial / bail / waterfall。

注意：cordis 4.0.4 里没有 ctx.require / ctx.define / ctx.using（对 cordis/src 全量 grep 无匹配）。可用面是 plugin / inject / extend / isolate / intercept / effect / get / set / provide / accessor / mixin / reflect。Plugin 只有三种形状：Function / Constructor / Object，没有 Plugin.Class。

DSH 在此之上加的是声明式装配层：一份 cordis.patch.yml 清单，用 insert / 按 id 覆盖 / group / disabled / isolate / !!js 描述"装哪些插件、哪些禁用、哪些服务要隔离"。

大白话

普通软件是一堵砌死的墙：砖和砖直接粘在一起。DSH 是乐高底板：每块积木只认底板上的凸点（服务键），不关心旁边是哪块。想换一块，拔下来插上去，别的不用动。

那份 YAML 就是拼装说明书。说明书本身还能被改写——用户目录里的 patch 会盖在出厂说明书上面。

两个值得单独说的细节

!!js 求值器的真面目

const evaluate = new Function('ctx', 'expr',
  'with (ctx) { return eval(expr) }')

cordis-plugin-loader/src/config/utils.ts

配置里的 !!js 表达式就是在插件自己的 ctx 上做 with(ctx) + eval。所以它能读服务（ctx.webStartup.port ?? 3080）、读 env（process.env.DSH_PERMISSION_MODE）、读宿主注入的全局（dshHomePath('sessions')）。DSH 把这份代价与收益都写进了文档：--dump-config-schema 只投影不求值，--dump-config 原样打印表达式。

volatile：让"改配置"不等于"重启插件"

schemastery 提供 Schema.prototype.volatile()（lib/index.mjs:235-237）与默认值 createVolatile(schema.meta.default)（:480）；loader 侧 equalExceptVolatile(previous, next, schema) 把标了 volatile 的字段视为相等（config/diff.ts）。

效果：改一个 volatile 字段 → 原地提交，不 remount。这是 DSH 能在运行中改模型、改端口、改工具配置而不打断会话的机制基础。

两个细节最能说明工程成熟度：
① config 整体替换、绝不深合并 —— 这是刻意选择的语义。深合并会让"改一个字段"变成"隐式依赖出厂默认值"，一旦出厂配置改动，用户 patch 就静默漂移。DSH 选择让你必须重述全部字段，把耦合暴露出来。

内核层：Agent 主循环与上下文装配

核心 · 最核心

这一层是 harness 的心脏。dsh-agent-loop（包内 JS 共 218,111 B）是公开 Agent 契约的唯一具体实现，它注册成 ctx.agents 上的 AgentFactory——也就是说，连"agent 本身"都是一个可替换插件。

专业表述

循环分两级：turn（轮） 与 step（步）。一个 turn 是"一次用户意图的完整处理"，内部可含多个 step；每个 step = 一次模型请求 + 该请求触发的工具执行。turn 边界处打开持久 turn，原子地领取 pending next-step 输入 + 一个排队 prompt；step 之间只领取 next-step 输入。

inbox 是持久投影而非内存队列：ReactLoopInbox 复用 Cordis 的 inbox 投影，每次变更提交一个规范化的 agent/inbox/spliced 事件，投影注册表同步折叠，因此在任何一个 Agent 存在之前、以及所有 Agent 卸载之后，冷读依然成立。

大白话

turn 是"回答你这个问题"，step 是"中间想一次"。你问一句，我可能想 5 次（每次想完干点事再想下一次），这 5 次算一个 turn。

待办队列不是存在内存里的清单，而是写进日志的账目。所以程序崩了重启，队列还在——因为队列本来就是日志的一个视图，不是另外一份状态。

系统提示词装配：32 个固定插槽

DSH 不用"拼字符串"的方式构造系统提示词。dsh-system-prompt 是一张带数值顺序的注册表：每个工具、每条策略各自认领一个固定插槽，装配时按数值排序。这样增删插件不会打乱提示词结构，也不会让缓存整体失效。

大白话

大模型有个省钱机制：前面说过的话如果一字不差，就不用重新算。DSH 非常在意这件事，所以它宁可"把新规则追加在后面"也不"把旧规则原地改掉"——原地改会让模型把前面全部重算一遍。

这也是为什么你在会话中途看到的工具列表变化时，DSH 会插一条 developer/message 说"新增了哪些、移除了哪些"，而不是把整份工具说明书重写。

这一层为什么是 DSH 的护城河

  • 日志是唯一真相源，且可重建请求。src/invariant.ts 是"invariant companion: request reconstruction from the session log"——DSH 内置了一个不变量检查，用来验证模型请求能从会话日志完整重建。这在 agent harness 里非常罕见。
  • turn/step 双层 + 持久 inbox，而不是一个 while 循环加一个消息数组。
  • 缓存经济学进入内核：request series、header 变更包、逐节点空替换、in-history 追加，都是显式概念。
  • 失败语义穷举：四种取消/失败码 + 明确的"能不能重试"指导语，直接写进给模型看的结果文本。

能力层：工具管线与 PTC 能力调用

核心 · 执行

DSH 的工具不是"函数 + JSON Schema"。它是一个带固定阶段、单调守卫、可取消语义、且 schema 不外泄的管线（dsh-tools，376,925 B / 12 文件）。

固定管线

为什么 pre-execute 故意不能改写 exec.arguments？README:230 明确写了这条限制，并链接到一份仍在提案阶段的设计记录 .agents/notes/proposed/feature/2026-06-30-pre-tool-input-rewrite.md。含义是：如果审批阶段能改参数，那么"用户批准的动作"和"实际执行的动作"就不是同一个动作了——审批失去意义。DSH 宁可让"改参数"这件事停留在提案状态，也不默认开。
专业表述

工具注册是 scoped layers（与 skills 注册表同构的 host+per-scope 形态）：ctx.tools.register / restrict / get / schemas。请求时把内部 ToolDefinition（output / execute / finalizeContent / timeoutMs / 展示回调）投影成面向模型的 ToolSchema——内部字段不外泄。

守卫是单调的（README:85）：注册顺序叠加，后注册的只能进一步限制，不能解除前一个的限制。

大白话

审批不能偷改你要做的事。你批准的是"删 A 文件"，那执行的就必须是"删 A 文件"，中间任何环节都不能悄悄换成"删 B 文件"。

守卫只能加锁不能开锁。十个人往一个门上加锁，任何人都不能把自己加的锁拆掉，也不能拆别人的。最后能不能开门，取决于所有锁是否都允许。

两个容易被忽略的设计决定

① "被拒绝"和"沙箱不可用"是两套语义

denied（命令跑了但被内核拒）与 SANDBOX_UNAVAILABLE（命令没跑）在 proc.sandbox 与 tool/result 上分开记录。这样"环境缺沙箱"不会被误报成"命令失败"。对模型来说这是两种完全不同的下一步：前者应换路径或申请升权，后者应报告环境不可用。

② 权限状态是会话日志的事件折叠，不是内存变量

permission/preset + sandbox/mode + approval/policy 三个事件折叠成 permissions 投影，因此可重放、可审计、跨 resume/fork 恢复。custom 是派生的"非预设"状态，永不是切换目标或事件载荷；auto 保留。审批本身有 approval/asked / approval/decided 成对审计且必须 turn-enclosed。

升权是执行期校验 + 一次性 + 必须带 justification：schema 不校验 mode 宽度，WIDER_MODES 在执行时判；justification 与 sandbox_permissions 必须成对出现；拒绝后明确写"stop and explain instead of working around it"。

数据层：会话即日志，日志即真相

核心 · 数据

DSH 的会话不是一个消息数组，而是一条带版本号的 append-only 事件日志。所有视图——对话界面、投影、查询、压缩后的上下文、子代理列表——都是从这条日志派生的。

专业表述

ctx.sessionPersistence 是"per-session handle 寻址的持久 append-only 会话存储"。agent 循环是会话写句柄的生产获取点：create 先调 persistence.create(header)（先落持久身份、先拿写所有权，再发布）；resume 先调 persistence.open(id, 'write')（排除并发 resume），再通过句柄读物理合法的日志。

发布后，挂载的后端把该会话的 session/event 批次、session/flush 屏障、session/disposed 退役，按 session id 路由到活跃写句柄。循环只通过它拥有的句柄触碰存储。

大白话

先记账，再承认这件事发生过。顺序是反过来的就出 bug：如果先对外发布、后写日志，中间崩了就会出现"界面显示有、日志里没有"的鬼状态。DSH 强制先拿到写权限、先落盘，再发布。

崩溃语义（README 原文要点）

  • create(header) 不写盘；首次 append 无覆盖发布 + fsync；每批次 append 前 fsync
  • 写/同步失败回滚到之前字节长度；已提交事件绝不重写
  • 撕裂尾由读方的写句柄追加合成 closer；撕裂的最后一个 zstd 帧只贡献完整解出的记录，写句柄截掉撕裂字节
  • 每会话每后端实例一个写者：POSIX 首次 append 用 link() 让同 id 竞态失败而不覆盖；Windows 用无替换 write-through rename

模型层：Provider 中立的调用接缝与凭据分离

核心 · 模型

DSH 里没有任何代码"调用 DeepSeek API"。它调用的是 ctx.llm——一个provider 中立的接缝。官方 README 一句话概括这一层的设计："the logical contract is provider-neutral, adapters own the wire."

专业表述

dsh-llm 定义 canonical 的 message / content-block / stream-chunk 词汇一次；每个 provider adapter 只负责把自己的 wire 格式翻译进这套词汇。注册表是拓扑所有者：adapter 路由、可配置 provider 条目、发现 offer 都注册在这里，并随其 fiber 一起析构。而 agent-loop 的请求始终是会话日志的纯函数——循环构造的请求以 deep-frozen 到达，监听者与 adapter 只能读、不能改写。

大白话

换模型供应商不用改主循环。主循环只说"我要一次流式调用"，具体怎么发 HTTP、字段叫什么名字，是各家 adapter 自己的事。

而且"发给模型的内容必须能从日志重建"是这一层的硬不变量：任何环节都不允许偷偷改请求内容。想改，就得写进日志。

为什么事件转发要区分 emit 与 waterfall

Cordis 事件有两种语义：emit 是广播（谁都可以响应，无返回值约定）；waterfall 是链式归约（每个监听者拿到前一个的结果，可以改写并传给下一个）。

user-questions/request 被转成 waterfall，因为"向用户提问"这件事只能有一个答案：多个 UI 监听者（Web 面板、CLI、SDK 客户端）串成一条链，谁先给出答案，答案就沿链返回。如果用 emit，就会出现"三个界面同时弹窗、三个答案互相覆盖"。

27 条转发事件里，模式字段就是 emit 或 waterfall——DSH 把并发语义显式编码进了协议，而不是留给实现去猜。

鉴权闭环：完整时序

agent-experience 技能全文透露的设计准则

这份技能是给"写工具的人"看的规范，它同时暴露了 DSH 的上下文哲学：

  • Start with minimal context：先暴露目的、可用动作、约束；需要时再加载细节
  • Make discovery explicit：每个延迟加载的资源都要有清晰描述和可靠取回方式
  • Keep critical constraints visible：权限、破坏性效果、必需校验要出现在相关动作之前
  • Prefer bounded outputs：返回带标识符/路径的简洁结果，不要整份日志或整篇文档
  • Use locality：结果附带有限量的相邻上下文（例：回复一条消息时带上前面几条）；省略与截断要显式标注
  • Delete obvious constraints：模型能从调用结果学到的规则（比如文件不存在会失败）不要写在工具描述里
  • Describe behavior, not implementation：省略内部机制、模型在结果里看到的输出标记、强制执行细节
  • Measure the change：改工具定义前后对比首轮 prompt token 数

四个更抽象、但更能说明问题的差别

① 把成本变成纪律

每个包的 README 都必须回答"模型看到什么 / token 影响 / KV Cache 影响"。这不是文档风格，是提交纪律——插件作者必须为自己的功能的上下文成本负责。

配套技能 agent-experience 甚至要求"改工具定义前后对比首轮 prompt token 数"。

② 把失败语义穷举到文本

取消/失败不是抛个异常，而是穷举错误码 + 写给模型看的重试指导语："Its outcome is unknown." / "只允许对只读或幂等操作重试" / "可能产生副作用的必须先查外部状态或问用户"。

这是在教模型如何诚实地面对不确定性。

③ 把"能力"与"授权"分开

DSH 提供 plugin-manager 工具但默认 disabled: true；提供 codex/claude-code/ralph 后端但默认禁用（且后端包并未随包分发）；提供 danger-full-access 但该预设把审批设成 never。

能力存在 ≠ 默认有权使用。这条边界在多数 harness 里是模糊的。

④ 把"谁有权决定"写进代码

三处最清楚：暂停的目标只有人类能重启；被委派的子代理被禁止问人（DELEGATED_CALLER，因为没有人会回答它）；升权只对本次调用生效且必须成对给出 sandbox_permissions + justification。

DSH 不是把权限当成"能不能做"，而是当成"谁有资格做这个决定"。

⑤ 把"装配"做成数据，而不是代码

一般 harness 的"装哪些模块"写在 import 语句和启动函数里。DSH 把它写在 YAML 行里，并且这份 YAML 能被上层 YAML 改、能按 id 覆盖、能整组隔离、能对活运行时求值。代价是复杂度，收益是不重新编译、不重启就能换掉一个能力——连前端面板都是插件。

配套证据：--dump-config 输出可重新加载的 YAML 并逐层标注来源；--dump-config-schema 输出装配清单自身的 JSON Schema。
