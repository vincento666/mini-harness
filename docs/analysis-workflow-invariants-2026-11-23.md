# 三论 workflow：三前提的保证机制、取代不变量集、结构化表达层

**日期**：2026-11-23 · **性质**：分析与设计建议（不是 OpenSpec 规格）· **前两篇**：`analysis-workflow-design-2026-11-23.md`、`analysis-workflow-paradigm-shift-2026-11-23.md`
**问题**（用户原问拆成三个）：① 如何保证三前提——「政策计算不交给模型、护栏在工具层不在提示词、升级链路先于自动化建好」；② 处理好哪些不变量后，harness workflow 能基本取代传统 workflow；③ 可视化建模能否通过 skill 反向推出或自带结构化表达层（构建时同步确认流程，skill 附件是流程图，节点执行是代码，跳转由 gate 控制）。
**约定**：事实与出处明确的机制放 §1–§3 的「事实」小节；设计建议全部标注；§6 强制分区。用户在本轮提出的结构化表达层构想记为「用户提议」，我的工作是把它落成可实现的形状并指出边界。

---

## 0. 先拆背景词

**gate（门）**。类比：**工序之间的质检站**——上道活没过检，下道不开工。技术定义：一个确定性判定表达式，只读「工具结果的字段」，输出 pass / fail，控制流程推进。关键性质：**它不是给模型看的提示，而是 runner 强制执行的代码**。

**不变量（invariant）**。类比：**无论怎么折腾都不许破的规矩**。技术定义：系统在任何执行路径下都必须保持的性质（本项目已有六条运行时不变量 A–F）。本篇讨论的是「workflow 层的不变量」——传统流程引擎天然满足、harness 必须显式复刻的那些性质。

**结构化表达层（structured expression layer）**。类比：**乐高图纸的零件表**——图是给人看的，零件表才是拼的依据。技术定义：skill 包内一份封闭 schema 的流程声明（节点 + gate 跳转），它同时服务三个消费者：运行时执行、渲染成流程图、人在构建时确认。

**派生视图（derived view）**。类比：**由零件表自动生成的装配图**。技术定义：流程图不手工画，而是从结构化声明渲染出来；两者永不漂移，因为图是生成物。

## 1. 三前提如何保证（机制化）

### 1.1 政策计算不交给模型

**责任分配是结构性的，不是纪律性的**：

| 角色 | 干什么 | 不许干什么 |
|---|---|---|
| 脚本 / 业务工具 | 算金额、判资格、取政策档位（产出结构化字段） | — |
| 模型 | 调用脚本、读结果、组织语言、收集信息 | **不得成为金额/资格结论的生产者** |
| gate | 用工具结果字段判定推进与否 | 不读模型文本作为证据 |

三个保证机制：

1. **证据只认工具结果**。gate 表达式只允许引用 `tool.<call_id>.<field>` 形态的字段（载荷经 pydantic 校验）；引用 `model.*` 的 manifest 在加载期直接拒绝（机制见 §3.3）。模型在回复里说「符合退款条件」不产生任何推进效力——这正是传统流程引擎「代码节点输出才是变量」的等价物。
2. **结果形状封闭**。政策脚本返回固定 schema（如 `{"eligible": true, "cap_cents": 20000, "policy_ref": "3.2"}`），不返回自然语言。这延续不变量 B（工具是能力契约）：脚本的「拒绝」也是结果词，不是异常。
3. **变异判据钉住这一点**。里程碑收尾的变异测试必须包含一类：**改写模型输出使其声称与脚本相反的结论 → gate 行为不得变化**。杀不死这条变异的测试就是覆盖缺口。

对抗性场景的验证口径（源自客服实践的红队共识，前篇实践 #10）：用户施压「给我多退点」时，正确行为不是「模型顶住了」，而是「模型要么重跑脚本、要么走升级」——因为**判定权根本不在模型手里**。

### 1.2 护栏在工具层，不在提示词

**核心论证**：提示词可被注入污染模型的「意图」，但污染不了「工具的执行约束」。所以护栏的定义是——**即使模型被完全劫持，损害也被工具层限死**。

mini 侧的强制点（事实：均为既有机制）：

| 强制点 | 机制 | 来源 |
|---|---|---|
| 参数上限 | 工具 schema 校验（如 `initiate_refund` 的金额参数带 max） | pydantic 入参校验（M4 起） |
| 管线守卫 | 六段管线的 `guard` 段：工作区边界、CAS、围栏判定 | M10 |
| 两轴分离 | `--sandbox` 与 approval 是独立轴；写操作默认 `ask` | 不变量 E |
| 子代不放行 | 子代理不继承 approval 放行，问人一律 `UNAVAILABLE` | M12 |
| 失败即结果 | `FenceCode` / 结果词落日志，不抛异常绕过审计 | 不变量 B |
| OS 级兜底 | 进程收容 / 文件写拒绝（需要时） | M15a / M15b（规划） |

设计规则（外部实践共识，CorePiper / QwickAI，前篇已引）：先给每个动作分类——可逆性 × 金额暴露 × 合规敏感——再映射到「工具参数上限 + approval 档位」。**「退款不得超过 X」写进工具 schema 与 gate，只把「语气与解释」留给提示词**。

验证口径：变异测试注入提示词攻击 fixture（如藏在用户消息或知识文档里的指令）→ 断言 **`tool/result` 返回限额拒绝**，而不是断言「模型回答得体」。前者可测，后者不可测。

### 1.3 升级链路先于自动化建好

**建设顺序就是保证机制**——顺序错了，机制再好也救不了：

```
第 1 步：升级通道端到端测通（handoff 模板 + 信号 + 平台侧接收）
第 2 步：影子模式（Act 类动作 approval: ask 全确认，人签每一次）
第 3 步：能力阶梯放权（答 → 查 → 确认后办 → 自主办），每上一级的前提是该级的升级演练已绿
第 4 步：才允许扩意图 / 扩渠道
```

机制保证（事实 + 设计混合）：

1. **升级永不设限**：`escalate` / `ask_user` 路径始终可用、**免审批、不计入能力白名单的裁剪**——preset 裁工具表时升级类工具不可裁（设计约束，待写进 skill-providers 规格）。
2. **gate 失败的默认去向是交回人类**，不是「再试一次」。M13 的 `blocked`（同一阻碍三轮）与停滞闸门（连续两轮零工具调用）是内核级兜底；workflow 级再加 `max_rounds`。
3. **交接载荷是 skill 包的一等公民**（`references/handoff-template.md`，前篇 §5.1）：意图、摘要、已试动作、置信度、依据、未决问题。G1 契约的 `handoff: {needed, reason}` 字段已有（G 轨规划口径）。
4. **判据**（UAT 必跑）：构造「所有 gate 全部失败」的场景 → 必须产出完整交接载荷、零伪造动作、日志里每步失败都有结果词。

一句话：**升级链路是第一条交付物，自动化是第二条**。倒过来做的团队会发现自己「自动化率很高、客户在重复解释问题」（外部实践指南反复警告的失败模式）。

## 2. 取代不变量集：八条处理好，harness workflow 就复刻了流程引擎

（本节为**分析框架**；每条左侧是传统流程引擎的原生保证，右侧是 harness 的复刻件。复刻件标注事实来源或「待建」。）

| # | 不变量 | 传统引擎的原生保证 | harness 复刻件 | 状态 |
|---|---|---|---|---|
| I1 | **推进只认 gate** | 节点按连线走完才出边 | phase 推进唯一准入点是 gate 判定；模型说「做完了」无效 | 待建（runner） |
| I2 | **判定可重算** | 流程实例数据可查 | gate 表达式只读日志内的工具结果字段，`replay` 能重新算出同一判定 | 待建（依赖 I1 的字段限定） |
| I3 | **能力≠授权** | 引擎内建权限检查 | 工具层强制（§1.2 表）；子代不放行 | **已有**（不变量 E、M12） |
| I4 | **失败即结果、去向确定** | 节点异常走错误边 | 结果词 + 终局三态：`complete / escalated / blocked`，无静默分支 | **部分已有**（不变量 B、M13；终局三态待收口） |
| I5 | **状态持久可恢复** | 流程实例落库、可续跑 | phase/goal 状态进 JSONL，`--resume` 同点续跑 | **已有**（M11 + M13） |
| I6 | **审计唯一真源** | 每步执行记录 | 全事件进 JSONL，`replay` 逐点相等 | **已有**（不变量 A/F） |
| I7 | **终止性显式** | 图有限，天然走完 | `max_rounds` + 停滞闸门 + AGENT_CAP 式上限（DSH 同构） | **部分已有**（M13；workflow 级上限待建） |
| I8 | **决策出处结构性** | 变量来自节点输出 | 金额/资格/身份的**生产者必须是工具或脚本**，**消费者必须是 gate**；schema 层禁止引用模型文本（§1.1 机制 1） | 待建（manifest 校验） |

**为什么这八条够了**：流程引擎对业务的全部承诺可以归纳为「有序、可控、可审计、可恢复、会停、责任清楚」——I1/I7 保有序与终止，I3 保可控，I2/I6 保可审计，I5 保可恢复，I8 保责任清楚。八条全绿时，前篇 §2 矩阵的 a–e 五项被完整复刻；f（可视化建模）由 §3 的结构化表达层补上；g（平台运维）本来就不在内核目标内。**这就是「基本取代」的准确含义**：取代的是流程引擎的语义保证，不是建模市场的产品形态。

一个诚实的边界：I1 与 I8 要求「判定权与叙述权分离」，代价是**每类办理动作都要有人先写脚本/工具**。传统流程图的成本是画图，harness 的成本是把政策写成代码——民航这类政策本就成文的领域，这个成本是搬移而不是新增；但零散、纯经验型的 SOP（无成文政策）短期仍留在「软路径 + 人工兜底」形态。

## 3. 结构化表达层：可视化建模的派生视图方案（回应用户提议）

### 3.1 主张（用户提议 + 我的确认）

用户提议：**构建时同步确认流程；skill 附件是流程图；每个流程节点的执行是代码；控制节点跳转的是 gate**。我认为这个方向成立，并把它收束成一条原则：

> **结构化声明（manifest）是唯一真源；流程图是从它渲染的派生视图；SOP 正文是给模型的软路径说明；三者冲突时，判定只认 manifest + 工具结果。**

这同时解决前篇矩阵第 f 项的缺口：可视化建模不必「被取代」，它从「独立资产」降级为「生成物」——图与执行永不漂移，恰好反制 Coze 教训（图是平台私产、与执行脱钩）。

### 3.2 真源方向的三种读法（我推荐 A）

| 读法 | 真源 | 图的地位 | 代价 |
|---|---|---|---|
| A（推荐） | manifest | 渲染生成，随包提交 | 业务人员不直接改 YAML——由「确认循环」弥补（见 3.4） |
| B | 画布工具 | manifest 由图导出 | 引入第二套建模工具，重蹈平台资产覆辙 |
| C | 双向同步 | 两者互为源 | 同步冲突无解，最危险 |

**「构建时同步确认」的机制**：propose/评审时渲染流程图放进提案给人看（贴合本项目 OpenSpec 人审流）；CI 里重渲染比对 hash，图与 manifest 不一致则报错。skill 附件的 `flow.mmd`（mermaid）是生成物，不是手画品。

### 3.3 节点与跳转的封闭词汇表（固定 schema，不是 DSL）

```yaml
# workflow.yaml —— 节点 + gate 跳转（示例形状，字段待裁）
version: 1
name: ca-refund
nodes:
  - id: check_eligibility
    kind: script          # 封闭枚举：script | tool | model | human | subagent
    run: scripts/check_refund_eligibility.py
  - id: ask_confirm
    kind: human
  - id: do_refund
    kind: tool
    call: pss_refund
    approval: ask
edges:                    # 跳转目标封闭：next | 具名节点（同阶段内）| escalate
  - from: check_eligibility
    to: ask_confirm
    when: "tool.check_eligibility.eligible == true"
  - from: check_eligibility
    to: escalate
    when: "tool.check_eligibility.eligible != true"
```

三条边界（与红线的对照，这一步必须诚实）：

1. **跳转目标封闭**：只允许 `next`、同阶段内具名节点、`escalate` 三种去向；**不允许任意跨边、不允许循环**。客服 SOP 的真实形状是「主干 + 例外出口」的树，这个词汇表覆盖得住。
2. **循环不是图引擎的循环**：批量重试类需求走 `fan_out`（P1 批量原语）或 goal 轮次（M13），不在 manifest 里画回边。真正需要任意图与状态机的 SOP——那正是 G 轨红线挡的「图引擎」，正确做法是把 SOP 重构成树，或保留为 agent 软路径。
3. **meta 是数据不是代码**（DSH 同构原则，本地一手材料）：manifest 里出现可执行逻辑（表达式超出口径、内嵌代码）加载期拒绝；gate 表达式只做「工具结果字段的布尔组合」这一种形态（即前篇开放问题 1 的读法 A，本篇建议维持）。

DSH 对齐点：`nodes[].kind: script` 对应 PTC 的「脚本派活」精神但**不引入 guest 运行时**（红线：不做工具面塌缩）；`edges.when` 是 DSH `phase()` + gate 的声明式合并；事件上 `workflow/phase` 沿用既有命名风格。

### 3.4 三个消费面

1. **运行时**：runner 读 manifest，节点派发到脚本/工具/`ask_user`/子代理，gate 判跳转——满足 I1/I2/I8。
2. **人审视图**：`render` 生成 mermaid/SVG 流程图，作为 skill 附件与 OpenSpec 提案插图——满足「构建时同步确认」。
3. **业务确认循环**（反向推出）：业务人员的 SOP 文本/口述 → 生成 manifest 草稿 → 渲染图 → 人确认或改口 → 再生成。图在这里充当**沟通界面**：业务看得懂图，工程师维护 manifest，两者由 hash 保证一致。

### 3.5 仍然不取代的部分

自由拖拽、多角色在线协作、版本审批流的**建模平台产品**——那是产品层的生意（认知四：Agent 进产品）。mini 要的只是「流程可视化作为可确认、可审计的派生资产」，§3 方案到此为止。

## 4. 综合：「基本取代」的验收清单

三前提（§1）× 八不变量（§2）× 结构化表达层（§3）合起来，给出可勾选的成立条件：

- [ ] 任一金额/资格结论能在日志中定位到脚本/工具结果（I8 + §1.1）
- [ ] 改坏 gate 判定 → 至少一条测试变红（变异判据，I1）
- [ ] 注入提示词攻击 → 工具层拒绝且有结果词（I3 + §1.2）
- [ ] 「全 gate 失败」场景 → 完整交接载荷 + 零伪造动作（I4 + §1.3）
- [ ] 硬杀中途 → `--resume` 同阶段续跑（I5）
- [ ] `replay` 逐点相等（I6）
- [ ] `max_rounds` / 停滞闸门保证终止（I7）
- [ ] 流程图与 manifest hash 一致，且人在构建时确认过（§3.2）
- [ ] 升级链路的端到端演练先于该 skill 的自动化放权（§1.3 顺序）

九条全绿 = harness workflow 在该 SOP 上「基本取代」传统 workflow 引擎的语义；第 9 条是放权闸门，不绿不扩。

6. **manifest 的跳转词汇表**：本篇建议封闭为 `next | 具名节点 | escalate`（树形，无回边）；若真实 SOP 出现「必须回跳」的形状，是重构 SOP 还是放开有限回跳（如 `retry: max 1`）？请裁决。
7. **render 校验失败的处置**：图与 manifest hash 不一致时，读法 A——skill 不加载（强）；读法 B——警告但可用（弱）。构建时确认场景倾向 A，日常会话场景倾向 B，是否分层（安装期强、会话期弱）？
