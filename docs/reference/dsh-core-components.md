**立档：2026-11-20**。用途：回答「模块化接缝（E2）与评测（E1）之前，DSH 的核心组件还差哪些」。只记**组件级**缺口，不重复各 change 的任务清单。

## 二、评测构建前的顺序

按 roadmap 的既有顺序，把「必须」项排成一条线：

1. **M13 收口**（本 change）：UAT 四场按 D15 改口后重跑；`rounds_started` / 队列 / 停滞语义在 host 与 chat 一致。
2. **命名对齐**（`align-turn-step-naming`）：在评测报告开始产出之前把 turn/step 钉死；否则第一版报告就会用错词，后面每份报告都要翻译。
3. **M15a 进程收容**：无人值守的评测会跑 `bash`；没有进程树收容，超时/取消会留下子进程，评测结果不可信。
4. **MEM1 基础记忆**：R1 要跨会话保留实验结论；E1 的 held-out 基线也要求「同一任务在不同会话里可复现」。
5. **E1 runner + 任务集 + 基线**：到这一步才有「测什么、怎么算通过」。
6. **E2 组件接缝**：在 E1 有基线之后做，才能验证「换组件不改内核、A/B 可归因」；接缝本身不产生新能力，只产生可替换性。
7. **R1–R4**：消费者。

**并行度**：2（命名）可以与 1/3 并行，但它改的是全局词，最好在 M15a 之前落，避免 M15a 的文档再改一遍。3 与 4 互不依赖，可并行。5 依赖 1–4 的**行为**稳定，不依赖它们的文档完成度。

## 三、workflow 类能力：不是核心前置

DSH 的 `workflow-ptc` / `dsh-tool-workflow` 是**编排面**：让模型写一段脚本，用 `agent()` / `parallel()` / `pipeline()` 派子任务。它建立在子代理、工具管线与日志之上，不是「没有它就跑不了会话」的部件。

- **现在不立项的理由**：E1 还没有 held-out 基线；没有基线就加调度策略或 workflow，无法判断它是变好还是只是变复杂（roadmap 对 R1 的同一判断）。
- **进入条件**：E1 有 runner 与基线、E2 能换 `SubagentPolicy`、并且有一个真实的「多子任务 + 依赖排序」场景。
- **届时的最小形状**：不复制 DSH 的脚本 DSL；先在 `subagent` 工具上做「一批并行 + 结果聚合」，把 workflow 当作调度策略的消费者，而不是新内核。

## 四、与 E2 的关系

E2 的首批组件里，`Provider` / `ApprovalGate` / `ToolPolicy` / `ContextPolicy` / `CompactionPolicy` / `FailurePolicy` / `MemoryStore` / `SkillCatalog` / `SubagentPolicy` / `Verifier` / `CommandRunner` 中，mini 已经有明确的接缝点（见 `docs/reference/e2-component-seams.md`）。**先补齐行为，再抽接缝**：M15a 的进程收容坐在 `CommandRunner` 上，MEM1 的 `MemoryStore` 按组件接口生出来；这两项做完，E2 才有真实的替换对象，而不是对空接口做抽象。
