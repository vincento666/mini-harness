# Workflow 的三种范式与 2026 年的收敛

**立档：2026-11-23。** 触发：Coze 企业版下线公告（2026-10-29），以及「harness 是不是 workflow 的替代品」这个问题。

## 一、事实：Coze 企业版下线

火山引擎官方公告（`docs.volcengine.com/docs/coze/coze-enterprise-offline-announcement`）：

| 阶段 | 时间 | 范围 |
|---|---|---|
| 停止新售 | 2026-11-30 | 企业标准版、企业旗舰版 |
| 旧版套餐下线 | 2026-12-31 | 旧个人进阶版、旧企业版、旧团队版；未使用部分自动退款 |
| 新版企业套餐下线 | 2027-12-31 | 新购、续费、增购席位的到期日均不得晚于该日 |

官方理由是「产品整合安排」；公开报道补充：扣子团队 2026-08 并入豆包体系，资源向豆包集中。公告明确会另行说明「对话、记忆、文件、编程项目、低代码工作流等资源」的导出与备份。

**这不是「可视化 workflow 失败了」**，而是「平台型 workflow 的资产与治理不在客户手里」。三条具体教训：

1. **资产不可迁移**：图、提示词、插件绑定画在平台上；停服时连导出方案都要等后续公告。
2. **治理不在自己手里**：权限、审计、数据边界由平台定义；企业只能接受或离开。
3. **承载不了开放任务**：路径一旦需要动态展开，图就爆炸；这是范式边界，不是产品缺陷。

同期行业数据：IDC 称仅 18% 的中国企业把智能体纳入核心业务流——市场远未定型，退场是「赛马结束」，不是「需求消失」。

## 二、三种范式

| | 可视化 workflow（Coze / Dify / HiAgent / n8n） | 程序化编排（LangGraph / CrewAI / AutoGen） | 自主 harness（DSH / Codex / Claude Code） |
|---|---|---|---|
| 流程由谁定 | 人预先画节点与连线 | 人写代码定义状态图与路由 | 模型运行时决定下一步 |
| 模型的角色 | 节点内的一个能力 | 图里的一个执行者 | 外层循环的决策者 |
| 确定性 | 高（同输入同路径） | 中（代码固定，模型输出不定） | 低（路径每次可能不同） |
| 可审计性 | 强（每步可见） | 中（要读代码与 trace） | 弱到中（靠事件日志） |
| 适合 | 路径清楚的标准化任务 | 复杂状态、需要回放与人工断点 | 开放任务、长时目标、代码修复 |
| 不适合 | 开放路径、动态协商 | 需要业务人员参与改流程 | 需要强可预测性与合规审计 |
| 谁是用户 | 业务/运营 + IT | 平台/后端工程师 | 工程师 |

## 三、2026 年的收敛：不是替代，是分层

AI Engineer World's Fair 2026 的共识被概括成一句话：**「The Harness Beats the Model」**——模型在商品化，价值落在 harness（工具、技能、上下文、权限、验证、成本）。

正在成型的标准栈是四层 + 两个底座：

```
Coding Agent（外层循环：接目标、计划、委派、验证）
   ├── MCP 工具（结构化访问外部系统）
   ├── Sub-agents（受作用域约束的子任务）
   └── Skills（过程知识：怎么做，含边界与验收）
Context layer（系统指令、工具 schema、记忆、检索）
Workflow layer（确定性编排：Specify → Design → Break down → Implement → Verify）
```

关键点：**Workflow layer 没有被取代，它下沉成了 harness 的一个底座**。上面那层 agent 负责「下一步做什么」，下面这层 workflow 负责「哪些步骤必须按顺序、哪些门必须过、什么算验收通过」。

企业侧的证据更直接：Coinbase（Forge）、Shopify（River）、Ramp（Inspect）都在自建 harness，同时继续用 Claude Code / Codex 做交互式开发。前者跑异步、可治理的流水线，后者跑工程师手边的探索。**自建的是控制面，外购的是执行力。**

### 谁为主：按「路径确定性」分，不按「新旧」分

| 任务 | 主导 | workflow 的角色 |
|---|---|---|
| 客服 SOP、审批、对账、批量文档处理 | **旧（workflow）为主** | 骨架：分支、人工断点、权限门、审计 |
| 工单排障、迁移、跨文件重构、开放式研究 | **新（harness）为主** | 只提供边界：验收条件、预算、禁区、回滚 |

一句话：**路径能画出来就以 workflow 为主；画不出来就以 agent 为主，workflow 退成护栏。**

### Skills 是两者的连接件

Skills 把「SOP 的一段」编码成可版本化、可发现、可组合的过程知识——比 workflow 节点更轻，比提示词更硬。企业把 SOP 从平台图里搬进自己的仓库（skills + MCP + 策略），就同时拿到了可迁移性与治理权。这是 Coze 退场后最直接的产品迁移路径。

## 四、对 mini 的启示

1. **mini 的定位是 harness，不是平台**：目标对象、事件日志、工具管线、权限与预算都在自己手里，模型可换。这正好是 2026 年收敛出来的那一层。
2. **goal 是「完成契约」，不是 workflow**：它只声明「什么算完」，不规定路径。这与可视化 workflow 的「预先画路径」是互补关系。
3. **workflow 类能力排在 E1 之后**：没有 held-out 基线时加编排，无法判断是变好还是只是变复杂（`docs/reference/dsh-core-components.md` 第三节）。
4. **届时做固定 schema 的批量原语，不做 DSL**：先覆盖 fan-out/fan-in 与 pipeline 两种模式；supervisor 式动态路由等有真实场景再说。
5. **Skills 与 MCP 是比 workflow 更优先的「新旧连接件」**：M14 已有技能注册表与命令面；把 SOP 沉淀成 skill，比再画一张图更可迁移。

## 五、不确定的地方

- Coze 下线后的企业客户流向没有公开数据；「三足鼎立」是媒体叙述，不是审计事实。
- 「40% 企业应用内嵌 agent（Gartner）」「2028 年 1/3 工作流完全 agentic」都是预测，不能当基线。
- 企业自建 harness 的案例来自公开访谈与报道，成本与效果数字未经独立核验。
