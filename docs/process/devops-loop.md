# 研发流程的对齐与自动化（提案）

**日期**：2026-11-16。**范围**：本仓库的 change 流程（propose → apply → 两轴 review → 三半验收 → 归档 → 合入）。本文只提议程，不改代码。

## 0. 统一范式：人只选弹窗，其余自动推进

**默认动作是继续，不是请示。** 在已批准的计划与 change 范围内，agent 一路做到下一个停点；人不再输入「继续」。

### 0.1 五个停点（只弹窗，其余不问）

1. **对齐**：范围、优先级、设计分叉需要人选；
2. **警告**：不可逆、破坏性、安全面、成本显著上升；
3. **复核**：子代理裁决出现 blocker，或两轴结论需要人接受/拒绝；
4. **决策**：merge `main`、UAT 归属、改 AGENTS/ADR/流程；
5. **事故**：证据不足、连续失败、计划外新需求。

弹窗格式固定：**what（这是什么）／why（为什么现在定）／how（选项与代价）／推荐项**。没有这四段就不许弹。

### 0.2 事故恢复

断电、退出软件、手动中止之后：先核 `git status` / HEAD / 活动 change，对照 `docs/CURRENT.md` 与当周计划，报「恢复到哪、下一步是什么」，然后继续——不重新请示已批过的范围。

### 0.3 验证契约（每个 change 的前置）

写实现之前先写一页验证契约，**人只审这一页**：

- **目标**：一句话，能被非实现者读懂；
- **可观察行为**：3–5 条，每条对应一个 seam；
- **判据**：每条行为至少一个测试/真实端点/CI 证据；
- **坏法清单**：3–5 个「做完但不对」的样子，作为变异种子；
- **不验什么**：明确排除项，防止范围漂移。

判据与目标对不上时，先改契约再写代码——这是视频说的「瓶颈在验证」在流程里的落点。

### 0.4 契约的双重复核与对照门禁

**问题**：契约写错，自动推进只会更快地把错误做完。解法不是「更小心」，而是让契约在写代码前被另一个上下文挑错，在写完后被逐条对照。

**第一道：契约复核（子代理，写代码之前）**

- 输入只给：目标、契约、对应的 spec / roadmap 段落；不给实现叙事。
- 五项检查：
  1. **可追溯**：每条目标都有可观察行为，每条行为都有判据；
  2. **可证伪**：每条判据都存在一种能失败的方式，禁止同义反复；
  3. **坏法覆盖**：至少 3 个「做完但不对」的样子；
  4. **范围**：`不验什么` 明确，且没有混入实现细节；
  5. **可读**：非实现者能读懂目标那一句。
- 输出：`PASS` 或 `GAPS`（每条 gap 带位置与 severity）。GAPS 先改契约，不进 apply；同一契约最多复核两轮，再不过升级为人裁。

**第二道：对照门禁（子代理，归档之前）**

- 输入：`git diff main...HEAD` + 契约；逐条映射证据（测试名 / 命令 / 输出）。
- 任一判据没有证据 = 未完成，不许归档。
- **只报影响正确性或既定需求的缺口，不报风格偏好**——这是 Anthropic 的告警：被要求找问题的审查者总会找出一些，穷追会导致过度工程。

**第三道：实现后的验证与测试**（已有）：四道门禁、真实端点、UAT、变异。仍出问题就修，或提新 change 迭代——不在一轮里无限返工。

**依据**：Anthropic 的 Claude Code 最佳实践明确要求「在视为完成前，让子代理在全新上下文审查 diff，只看 diff 与标准」；其 Building Effective Agents 把「生成者 / 评估者两个独立调用 + 循环」列为 evaluator-optimizer 模式。mini 把这两条落成「契约复核 + 对照门禁」两次独立调用。

### 0.5 模型能力适配

- 不假设模型能自证正确：所有「完成」由外部判据（测试、CI、真实端点、UAT）确认；
- 人的注意力放在**验收标准与分叉**，不放实现细节；
- 判据不足时先补判据，不许先写实现；
- 连续两次同一处失败，升级为停点 5（事故），不再自行重试。

## 2. 需要新增的四件事

### 2.1 阶段进入对齐单（由 grill-me / grilling 执行）

在 roadmap 的关键阶段进入前（下一个是 **M14c**，之后 M13、MEM1、E2、H 轨），propose 之前先答六问，答案由人给、agent 不得自答：

1. 这个阶段的**非目标**是什么（明确不做）？
2. 验收判据里，哪一条最可能被「做完但不对」地满足？
3. 有没有需要先补的一手调研？
4. 有没有会动现有规格或不变量（A–F）的改动？
5. 本轮**预授权**的简化/欠账范围是什么？
6. 范围上限：几个切片、什么条件下停？

产出写进 proposal 的「人裁决」小节。六问只问一次，不反复 grill。

**grill 入口**：技能已装（实体在 `~/.agents/skills`，各 harness 链接引用）。`grill-me` 是斜杠入口（`disable-model-invocation: true`，只由人触发），模型侧对应 `grilling`。两者都只是**提问器**，产出必须落成上面六问的答案并写进 proposal 的「人裁决」小节，不能替代人裁决。分诊 loop 的「候选简报」是六问的输入。

**为什么不挂 universal-work-loop**：它是完整的 Loop 工程实现（契约、门、角色、恢复一整套），mini 只保留简化流程；两套循环并存会让「哪套在管事」变得含糊。形式类似即可，物理上不引用。

### 2.2 决策点弹窗的触发清单

必须弹窗（AskUserQuestion）的六类：

1. **规格级偏差**：与 roadmap 或主规格文字不一致；
2. **不可逆 / 破坏性**：删文件、改日志语义、改 A–F 不变量；
3. **形状变更**：新增事件类型/字段、改 payload；
4. **规则变更**：AGENTS.md、ADR、流程文档；
5. **人的闸**：merge main、UAT 归属、会花钱的批量真实端点；
6. **范围扩张**：超出 proposal 的「非目标」。

约束：**每个检查点最多一次弹窗**，把同类问题合并成一次多选，避免疲劳。

### 2.3 单一出口物：Gate Report

每个 change 一份 `docs/verification/<id>-report.md`，只做索引、不复述细节：

- 四道门禁：命令 + 实测数字（passed / skipped / 覆盖 TOTAL / ruff / mypy）；
- 三半验收：mock / 真实端点 / UAT 各自的状态与链接；
- 记账清单：`blocker` / `debt` / `nit` 三级，每条带处置与触发条件；
- 未决项：等谁裁、触发条件是什么。

细节仍在现有五份文档（uat / real-endpoint / mutation / code-review / dsh-review）里，report 只做目录。

### 2.4 检查点播报（固定四个时点）

propose 后、每个切片提交后、三半收尾后、归档前。每次三行：**门禁数字 / 新增记账 / 待你裁决**。

## 8. 独立复核：用编码 harness 的子代理，不用 mini 自己的

**为什么**：同一个上下文里先写实现再审查，模型会倾向于认可自己刚写的东西（self-preference）；视频把「瓶颈在验证」单列，METR 也显示当前 AI 主要在「辅助」而非「自主」。所以复核要换一个上下文，而不是换一套提示词。

**怎么做（最轻但够用）**：

1. **触发**：改规格、不变量（A–F）、安全面的 change 必做；纯文档改动可跳过，但要在报告里写明「跳过，理由……」。
2. **输入只给三样**：change id 与 spec delta 路径、`git diff main...HEAD`、两轴（Standards / Spec）的定义。**不给**我的实现叙事与结论。
3. **只读**：子代理不得写文件、不得跑会改文件的命令；只能读与跑只读命令。
4. **输出契约**：`verdict`（PASS / PASS WITH FINDINGS / BLOCK）+ `findings`（severity: blocker / major / minor，每条带 `文件:行`）。
5. **记录**：原文贴进 `<change>-code-review.md` 的「子代理裁决」节；我不得改写它的结论，只能逐条处置（接受 / 拒绝 + 理由）。
6. **兜底**：harness 没有子代理能力时，退回同上下文自审，并在报告里标注「未隔离」。

**用哪个 harness**：用当前编码环境（WorkBuddy，未来可能是 DSH）自带的子代理能力，**不是** mini 自己的 `subagent` 工具——后者是被测对象，不能既当运动员又当裁判。

**实例**：2026-11-16 的 CI 连续三次红，原因是本地只跑了 `ruff check`、漏了 `ruff format --diff`；CI 在另一个环境里充当了独立复核，抓到了本地自审漏掉的一道门禁。

**成本**：一次子代理调用；不计入门禁，但计入当轮记账。

视频的判断与此相符：个人开发者或小团队在有明确方向、能拿到直接反馈时可以把 loop 跑起来；面向生产级基础设施仍需要人的经验判断与验证。所以 mini 保持人闸，只把**复核**与**触发**自动化。

## 10. 向人提问的上下文契约

当前审核的人可能不熟悉 DSH / harness / 门禁这些术语。每次请你裁决，必须带齐四段：

1. **这是什么（what）**：一句话解释涉及的机制，不假设你知道 DSH 是什么。
2. **为什么现在要定（why）**：不定会卡在哪一步、代价是什么。
3. **选项与代价（how）**：每个选项一句话说清代价，不写代号。
4. **一句话背景**：如果这个概念对你是新的，补一句类比或最小定义。

禁止只给结论、只给代号（例如只说「surfaceOp」）、或把「我的建议」写成「已经定了」。

## 13. 推进授权与角色隔离

### 14.1 人只决定，agent 自动推进

在**已批准的计划与 change 范围**内，agent 连续推进，不逐步请示：

- 自动做：一手调研、propose 起草、apply（红→绿切片）、跑四道门禁、两轴审查、对齐复核、三态验收里的真实端点、归档、推 `change/<id>` 分支。
- 人来定：六类升级点（见 §8.1）、计划变更、UAT 归属、merge `main`、改 AGENTS/ADR/流程规则。
- 停止条件：六类升级、merge、UAT、计划外的新需求。除此之外**不问「要不要继续」**，直接做并阶段播报。
