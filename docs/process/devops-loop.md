## 2. 需要新增的四件事

### 2.1 阶段进入对齐单（替代 grill / explore）

在 roadmap 的关键阶段进入前（下一个是 **M14c**，之后 M13、MEM1、E2、H 轨），propose 之前先答六问，答案由人给、agent 不得自答：

1. 这个阶段的**非目标**是什么（明确不做）？
2. 验收判据里，哪一条最可能被「做完但不对」地满足？
3. 有没有需要先补的一手调研？
4. 有没有会动现有规格或不变量（A–F）的改动？
5. 本轮**预授权**的简化/欠账范围是什么？
6. 范围上限：几个切片、什么条件下停？

产出写进 proposal 的「人裁决」小节。六问只问一次，不反复 grill。

**关于 grill 技能**：本机没有安装（实测 `~/.workbuddy/skills` 为空，仓库也没有）。六问清单就是当前的对齐器；如果以后装了 grill 类技能，它仍要产出同样的六问答案并落进 proposal，不能替代人裁决。分诊 loop 的「候选简报」是六问的输入。

### 2.2 决策点弹窗的触发清单

必须弹窗（AskUserQuestion）的六类：

1. **规格级偏差**：与 roadmap 或主规格文字不一致；
2. **不可逆 / 破坏性**：删文件、改日志语义、改 A–F 不变量；
3. **形状变更**：新增事件类型/字段、改 payload；
4. **规则变更**：AGENTS.md、ADR、流程文档；
5. **人的闸**：merge main、UAT 归属、会花钱的批量真实端点；
6. **范围扩张**：超出 proposal 的「非目标」。

约束：**每个检查点最多一次弹窗**，把同类问题合并成一次多选，避免疲劳。

### 2.3 单一出口物：Gate Report

每个 change 一份 `docs/verification/<id>-report.md`，只做索引、不复述细节：

- 四道门禁：命令 + 实测数字（passed / skipped / 覆盖 TOTAL / ruff / mypy）；
- 三半验收：mock / 真实端点 / UAT 各自的状态与链接；
- 记账清单：`blocker` / `debt` / `nit` 三级，每条带处置与触发条件；
- 未决项：等谁裁、触发条件是什么。

细节仍在现有五份文档（uat / real-endpoint / mutation / code-review / dsh-review）里，report 只做目录。

### 2.4 检查点播报（固定四个时点）

propose 后、每个切片提交后、三半收尾后、归档前。每次三行：**门禁数字 / 新增记账 / 待你裁决**。

## 3. 与现有规则的冲突点

- **UAT 代跑**：ADR-0025 要求人坐终端。M14a / M14b 的代跑都有你的明确指示，这是合规的；把它写成「默认我跑」就越界了。建议保留**逐 change 询问**，我在每次 UAT 前弹一次。
- **全自动 merge**：仓库明确规定 merge 与推 main 先征求批准，这是唯一防「未审代码进主干」的闸，不建议自动化。
- **自动改 AGENTS.md**：一进一出必须人裁，否则规则会自己长胖。

## 5. 可简化/合并的

1. **五份验证文档 → 加一份索引**：不合并细节，只减少「找不找得到」的成本。
2. **lessons 收件箱 29 → 6 类**：判据形状 / 环境 / 缓存 / 工具 / 规格 / 审查；合并同类、删已被代码自证的条目。
3. **两轴 review 与对齐复核去重**：对齐复核只列 DSH 十项与偏差，不再重复 proposal/design/spec 三行。
4. **UAT 场次允许 propose 后修改，但表里必须留「为什么改」**：M14b 的 S1 就从 `read` 改成了 `grep`。

### 8.1 升级清单（human-in-the-loop 的六类触发）

平时是 **human-on-the-loop**：在已接受的范围里自己诊断、补红、修技术问题、重跑门禁。出现以下六类才升级到人裁：

1. 值或行为无法从已接受的事实推导；
2. 范围或优先级要变；
3. 架构、公开契约、数据、权限、安全、成本、外部依赖需要实质决策；
4. 不可逆或生产动作需要授权；
5. 出现高影响事故；
6. 有界、有证据的尝试仍无法推进。

### 8.2 读量规则（他们的 context-pack 的极简替代）

## 8. 独立复核：用编码 harness 的子代理，不用 mini 自己的

**为什么**：同一个上下文里先写实现再审查，模型会倾向于认可自己刚写的东西（self-preference）；视频把「瓶颈在验证」单列，METR 也显示当前 AI 主要在「辅助」而非「自主」。所以复核要换一个上下文，而不是换一套提示词。

**怎么做（最轻但够用）**：

1. **触发**：改规格、不变量（A–F）、安全面的 change 必做；纯文档改动可跳过，但要在报告里写明「跳过，理由……」。
2. **输入只给三样**：change id 与 spec delta 路径、`git diff main...HEAD`、两轴（Standards / Spec）的定义。**不给**我的实现叙事与结论。
3. **只读**：子代理不得写文件、不得跑会改文件的命令；只能读与跑只读命令。
4. **输出契约**：`verdict`（PASS / PASS WITH FINDINGS / BLOCK）+ `findings`（severity: blocker / major / minor，每条带 `文件:行`）。
5. **记录**：原文贴进 `<change>-code-review.md` 的「子代理裁决」节；我不得改写它的结论，只能逐条处置（接受 / 拒绝 + 理由）。
6. **兜底**：harness 没有子代理能力时，退回同上下文自审，并在报告里标注「未隔离」。

**用哪个 harness**：用当前编码环境（WorkBuddy，未来可能是 DSH）自带的子代理能力，**不是** mini 自己的 `subagent` 工具——后者是被测对象，不能既当运动员又当裁判。

**实例**：2026-11-16 的 CI 连续三次红，原因是本地只跑了 `ruff check`、漏了 `ruff format --diff`；CI 在另一个环境里充当了独立复核，抓到了本地自审漏掉的一道门禁。

**成本**：一次子代理调用；不计入门禁，但计入当轮记账。

视频的判断与此相符：个人开发者或小团队在有明确方向、能拿到直接反馈时可以把 loop 跑起来；面向生产级基础设施仍需要人的经验判断与验证。所以 mini 保持人闸，只把**复核**与**触发**自动化。

## 9. 定时 loop（L0/L1，只报告不改代码）

对应 yetone 四级放权里的前两级。两条候选：

| 任务 | 频率 | 做什么 | 明确不做 |
|---|---|---|---|
| 每日观察 | 每天 09:00 | 扫活动 change 的未勾 task、最近一次 CI 结论（`gh run list`）、分支落后 `main` 的提交数；输出 10 行摘要 | 不改代码、不提交、不合并 |
| 每周经验 | 每周一 09:30 | 扫 lessons 收件箱条数、Seen ≥3 未晋升的条目、归档体积；输出归并建议 | 不改 AGENTS.md、不删条目 |
| 需求/PR 分诊 | 每周一 09:45 | 扫开放 PR / issue 与下一里程碑，逐条分类；对候选给一页对齐简报（what/why/how + 三问） | 不建 change、不写 proposal、不合并、不回复、不打标签 |

时区按本机（Asia/Shanghai）。日程要人确认后才建。

**分诊不是 propose**：定时任务只做分类与简报，change 的创建与 proposal 必须等人在 grill 对齐里回答后由 agent 起草。分诊结果为空时只输出一行「无新 PR / issue；下一里程碑：X」，不制造噪声。

## 10. 向人提问的上下文契约

当前审核的人可能不熟悉 DSH / harness / 门禁这些术语。每次请你裁决，必须带齐四段：

1. **这是什么（what）**：一句话解释涉及的机制，不假设你知道 DSH 是什么。
2. **为什么现在要定（why）**：不定会卡在哪一步、代价是什么。
3. **选项与代价（how）**：每个选项一句话说清代价，不写代号。
4. **一句话背景**：如果这个概念对你是新的，补一句类比或最小定义。

禁止只给结论、只给代号（例如只说「surfaceOp」）、或把「我的建议」写成「已经定了」。
