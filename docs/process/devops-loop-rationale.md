## 2. 为什么不挂 universal-work-loop

`universal-work-loop` 是完整的 Loop 工程实现（契约、门、角色、恢复一整套），mini 只保留简化流程；两套循环并存会让「哪套在管事」变得含糊。形式类似即可，物理上不引用。

## 3. 与既有规则的冲突点

- **UAT 代跑**：ADR-0025 要求人坐终端。M14a / M14b 的代跑都有人的明确指示，这是合规的；把它写成「默认我跑」就越界了。保留逐 change 询问。
- **全自动 merge**：仓库明确规定 merge 与推 main 先征求批准，这是唯一防「未审代码进主干」的闸，不自动化。
- **自动改 AGENTS.md**：一进一出必须人裁，否则规则会自己长胖——2026-11-17 的自检发现流程文档 `+309 / −11`（28:1）而 `AGENTS.md` 为 `+289 / −192`（1.5:1），即这条纪律此前只作用在 AGENTS.md 上。
- **归档必须在分支上做**：先合并再归档会在 `main` 上留下「代码已合、主规格还停在上一个里程碑」的窗口。这条理由从 `AGENTS.md` 搬到这里，规则本身留在 `AGENTS.md`。

## 7. 独立复核为什么换上下文

同一个上下文里先写实现再审查，模型会倾向于认可自己刚写的东西（self-preference）；视频把「瓶颈在验证」单列，METR 也显示当前 AI 主要在「辅助」而非「自主」。所以复核要换一个上下文，而不是换一套提示词。

**依据**：Anthropic 的 Claude Code 最佳实践要求「在视为完成前，让子代理在全新上下文审查 diff，只看 diff 与标准」；其 Building Effective Agents 把「生成者 / 评估者两个独立调用 + 循环」列为 evaluator-optimizer 模式。mini 把这两条落成「契约复核 + 对照门禁」两次独立调用。

**成本**：一次子代理调用；不计入门禁，但计入当轮记账。

视频的判断与此相符：个人开发者或小团队在有明确方向、能拿到直接反馈时可以把 loop 跑起来；面向生产级基础设施仍需要人的经验判断与验证。所以 mini 保持人闸，只把复核与触发自动化。

## 8. 本机技能布局

- **实体只放一处**：`~/.agents/skills`。`~/.claude/skills`、`~/.workbuddy/skills`、`~/.dsh/skills` 都是指向它的符号链接。
- **更新**：matt 库用 `uv run python scripts/sync_matt_skills.py`（幂等）；DSH 自带技能由 DSH 应用更新，链接自动跟随。
- **原则**：新技能先落 `~/.agents/skills`，再由各 harness 链接；禁止在两个 harness 目录各存一份实体。
- **已明确不挂**：`universal-work-loop`（与本项目简化流程不同层，避免混淆）；它的源码仍留在 `~/.codex/skills`，未删除。

## 9. 工期口径

- 按**个人 AI coding 速度**排：一个 change 0.5–2 天，不按传统人日/周计。
- 计划按天排、按周收口；未完成就顺延，并优先砍非目标，不砍验收。
- 当周计划写在 `docs/plan-YYYY-Www.md`，每日 09:00 的观察任务读它。
