# 工具并发按能力类别 + 独占 barrier；省上下文靠结果预算与剪枝，不靠并发

工具定义带一个并发类别：只读/网络类是 `parallel`（同一时刻最多 8 个），会改动/独占类是 `exclusive`（同一时刻 1 个，并且是 barrier——它之前的调用先完成、它之后的调用等它完成）；结果仍按完成顺序落盘，`tool/call` 仍按声明顺序。**并发解决的是 wall-clock，不是 token**：省上下文靠单条结果的输出预算（`read` 的行数已有、补字节上限；`bash` 的 16 KB；`grep`/`glob` 的字节上限）、spill 文件、单条剪枝与整段压缩；两者在 E1 里分开量。

Considered options：给每个工具配并发数——否，没有证据说明需要，配置面先长出来只会增加正交性；去掉 barrier、让改动与只读完全并行——否，读后写/写后读的一致性会从「调度保证」退化成「碰巧」；把上限从 8 调大——否，E1 没量到瓶颈之前不动；跨会话缓存工具结果——否，CAS 与工作区边界都要求「这次读到的就是这次看到的」。

Consequences：`ToolDefinition.mutates` 要么扩成 `concurrency` 类别、要么保留 `mutates` 并在派发段映射，二选一在 M10 定；保守 barrier 会让「读 → 写 → 读」的长批次多等一轮，E1 记录 wall-clock 与最大并发数再决定要不要更细的调度；`read` 的默认范围与 spill 路径是产品决定，要在 M10 的 spec 里写死，不能留给实现顺手决定。
