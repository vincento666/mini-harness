# 预算读数两个来源、溢出两条触发路径，默认触发线 54272 不是笔误

窗口预算要判「装配出来的上下文有多大」，裁决三件事。**读数来源两个**：装配后的消息按 `ceil(字符数 / 4)` 估算，同时用 provider 报回的 `usage` 校准（排除带 `purpose: compaction` 的回复与被遮蔽范围内的回复），两者取较大者。**溢出两条触发路径塌成同一个结果**：估算越线且一次压缩救不了，以及 provider 直接报 `error.code == "context_length_exceeded"`，两者都写 `error/context` + `CONTEXT_WINDOW_EXCEEDED` + 退出码 4，且都不为溢出结果调用回合模型。**默认触发线是 54272 而不是 102400**：公式 `floor(min(W × 0.8, W − O − 65536))` 里那个 65536 是给「这一回合还没产出的东西」（模型回复与工具输出）留的余量，照 DSH 的 `headroomTokens ?? 65536`；窗口 128000、预留 8192 时这一支比 `W × 0.8` 小，所以 54272 生效。

Considered options：引真正的 tokenizer（否：重依赖，且它的分词与目标模型的分词不一致，估出来的数照样要校准）；只信 provider 的 `usage`（否：装配发生在请求之前，请求还没发就没有数可信，而压缩必须在装配之内决定）；把 headroom 做成参数（否：它是实现常量，不是用户可调的窗口参数，`--window` / `--reserve` 两个够了）。

Consequences：`字符数 ÷ 4` 对中文严重低估（一个汉字算 1 个字符、实际约 1 至 2 个 token），所以压缩触发偏晚，真实兜底是 provider 报错那条路径；这条偏差在 M5 的人手验收里可观察，不修——修它要先选一个与模型一致的分词器。M5 的模型层验收量到了实测值：同一次装配估算 19991、校准读数 33871、provider 事后回报真实 `input_tokens` 44873，估算偏小 2.24 倍，校准收窄到 1.32 倍——校准用的是上一次请求的数，天然滞后一回合（数字与出处见 `docs/verification/m5-context-budget-compaction-manual.md`）。

**本条被 ADR-0019 部分接管（2026-10-21，M6）**：「两条触发路径塌成同一个结果」仍然成立，但那个结果只到回合级——provider 报出的超限先做一次请求级压缩再重试一次，`session/end` 与退出码归入口，「+ 退出码 4」只成立于 `run` 入口。
