# 溢出判据是压力预算 `W − O`；触发线只决定这次装配要不要尝试压缩

M5 起「这次装配要不要压缩」与「这份上下文装不装得下」用的是同一个数：触发线 `floor(min(W × 0.8, W − O − 65536))`。窗口小于 `(O + 65536) / 0.84` 时它比保留预算 `W × 16 / 100` 还小，于是每次装配都越线、而遮蔽范围恒为空——压缩不可能发生，会话照样以退出码 4 收尾，尽管那份上下文离窗口还远（实测 `--window 70000 --reserve 100` 读数 27444、压力预算 69900、保留预算 11200，M5 真实验收那一次读数 5933 就是这么死的）。裁决：**两件事拆成两个数**——溢出判据是压力预算 `W − O`，触发线只决定这次装配要不要尝试压缩；启动校验跟着从 `W − O − 65536 ≤ 0 → 退出码 2` 换成 `W − O ≤ 0 → 退出码 2`。

Considered options：把 65536 从触发线公式里删掉（否：它是给「这一回合还没产出的东西」留的余量，照 ADR-0016；删了压缩就几乎不触发）；把窗口下限抬到 78138 让死区走不到（否：那是用参数掩盖判据错位，小窗口恰恰是人拿来试的形状，而且 `--reserve` 一大门槛还要更高）；保留旧启动校验、只改溢出判据（否：那条校验的理由是「触发线为正才跑得起来」，而触发线为正不再是跑得起的条件——`--window 4000 --reserve 100` 触发线为 0、压力预算 3900，跑得起来且判据要跑它）。

Consequences：`--window` 的合法范围放宽到 `W > O`，触发线为 0 从「配置不成立」变成「每次装配都尝试压缩」；溢出的 `detail` 必须同时给预算读数、压力预算、触发线三个数，否则读日志的人判断不了「离窗口还有多远」，措辞也从两种变成三种（真写过摘要 / 给不出遮蔽范围 / 给得出却本身就装不下）；`CONTEXT_HEADROOM_TOKENS` 在 CLI 层不再被读，只活在 `trigger_line` 里。ADR-0016 那句「估算越线且一次压缩救不了」按本条读：越的是压力预算，不是触发线。真端点上撞不到「压缩之后仍不够」——摘要要超过压力预算的约八成才撞得到，而真模型写摘要恰恰是把它缩短（实测 `tokens_after` 106），那条分支只有 mock 判据覆盖。

**2026-10-26 补一条：连 mock 的「第二段开局压缩、压完仍超线」这个形状也成了不可达。** 原因是两个数的大小关系反了——压缩的保留尾部是 `0.16W`，压力预算是 `W − O`；只要 `O < 0.84W`（正常配置都是），压缩把对话体压到保留尾部之内之后一定落在压力预算之下，第二段于是正常收尾。反过来说，要让压缩之后的读数仍超过压力预算，就得 `O > 0.84W`，而那时**头部本身就超**，第一段也溢出，「只有第二段溢出」构造不出来。`fix-chat-screen-feedback` 那两条按旧触发线写的判据（「第二段溢出」与「只有一段溢出」）因此在 rebase 之后空转，已退休成 skip，断言并入「第一段溢出那一行带 detail」那条判据；详情见 `docs/adr/0002` 的判据欠账一节。
