# 设计：goal-round-pacing

## D1 `MAX_STEPS` 是轮边界，不是失败

`NO_CONTINUE_REASONS` 现在有五项：`ABORTED`、`FENCE_DENIED`、`PROVIDER_ERROR`、`CONTEXT_WINDOW_EXCEEDED`、`MAX_STEPS`。前四项都是「这一轮没能正常完成」；`MAX_STEPS` 不是——它只说明「这一轮把步数用完了」，模型与工具都正常。

把两者混在一起，等于让「预算用尽」承担「任务失败」的后果：解除武装、不续轮、目标悬空。改名之后这个错误才显形：`MAX_TURNS` 时代它数的是轮，用完确实该停；`max_steps` 时代它数的是轮里的步，用完应该换一轮继续。

所以 L3 只改一处：从集合里删掉 `MAX_STEPS`。其余四项保留——取消、围栏拒绝、provider 失败、上下文溢出都不该自动重试，它们需要人或外部条件变化。

## D2 不改 `turn/end.stop_reason` 词表

`MAX_STEPS` 仍是本轮的事实：日志要能回答「这一轮为什么结束」。驱动怎么解释这个事实是**策略**，不是事实。把词表改成 `ROUND_BOUNDARY` 之类会同时丢掉「是不是撞了步数上限」这条信息，replay 与统计都会变钝。

同理，`turn/end` 的 `steps` 与 `tool_calls` 不动；`step/end` 的 `MAX_STEPS` 不动。

## D3 L0 走 `append_system_prompt` 的默认值，不改 `SYSTEM_PROMPT`

三个候选落点，只有第三个同时满足「模型看得到」与「旧日志 replay 不断」：

| 落点 | 模型看得到 | 旧日志 replay | 结论 |
|---|---|---|---|
| 改 `SYSTEM_PROMPT` 常量 | 是 | **断**：`context/assembled` 里存了系统提示全文，重算对不上（L-097 已踩过） | 否决 |
| `create_goal` 的返回结果里附政策 | 是（只在创建那一刻） | 安全（`tool/result` 是 durable，replay 不重算） | 可用，但太晚、太窄 |
| `append_system_prompt` 默认值 | 是（每个会话开头） | 安全：它写进 `session/start`，`fold._start_facts` 从日志读；旧日志是空串 | **采用** |

代价写清楚：

- 所有**新**会话都带这段政策，包括没有目标的 `run` 与子代理。文本里用「若你有 `create_goal` 工具」的条件句，避免误导。
- 用户显式 `--append-system-prompt` 会**覆盖**默认（层叠语义是 flag > config > default），政策段随之消失。这是用户自担的覆盖，不在运行时强行拼接——否则「追加段」会变成两段来源，规格要重写。

## D4 不做 L1 / L2

DSH 的约束在三处：创建即武装、目标轮正文的收尾三选一、`tool:goal` 政策段。没有「工具描述里写建完就停」，也没有「创建后拒绝后续工具」。按对齐纪律，mini 不新增 DSH 没有的硬约束——尤其是 L2，它会误伤「建完目标顺手读个文件」的合理动作。

## D5 风险与边界

- **成本上限变了**：总步数从 `max_steps` 变成 `max_steps × max_rounds`。默认 8×32=256 步；部署若调大 `max_rounds`，要同时看 token 预算。这是有意的：长任务本来就需要更多步，之前只是被第一轮的上限截断了。
- **人类轮也会续**：人类轮撞 `MAX_STEPS` 且目标 active 时，驱动会开第 1 目标轮。这是期望行为——人类轮的 8 步用完了，目标轮接着干。但 `rounds_started` 会从 0 跳到 1，目标轮正文说 `Round: 1/…`，与「人类轮已经干了 8 步」不矛盾（轮次只数自动轮）。
- **模型仍可能「一轮里硬撑」**：L3 不阻止模型在一轮里做很多事，只保证「做不完时不会死」。真正的粒度控制是 L4，留给后续。
- **停滞闸门不变**：`stall_rounds` 只看目标轮零工具调用；L3 之后目标轮更容易出现，闸门仍有意义。
- **`MAX_STEPS` 之后模型可能误以为失败**：政策段明确「写满只是本轮结束，不是失败」，目标轮正文也已有「本轮结束前三选一」。两处口径要一致，测试里断言政策段与 `render_goal_round` 不冲突。

## D6 与 L4 的边界

L4 要做的是「一轮里最多写几次文件 / 调几次工具」这类**工作量预算**，不是「步数上限」。它与 L3 正交：L3 决定「写满之后怎么办」，L4 决定「一轮能写多少」。等 L3 落地后看真实日志，如果仍然出现「一轮 8 步写三篇」但轮次粒度不够，再开 `goal-round-budget`。
