## Context

`budget_reading` 有两个来源：估算，和「未被遮蔽的非 compaction `model/response` 里最大的 `input_tokens` 回报」。第二个来源是为了让读数贴近 provider 侧的真实用量——估算把 4 字符当 1 token，真实 tokenizer 不认这个近似。

问题在第二个来源的**时效**：一条回报描述的是产生它的那次请求。压缩之后，那次请求的上下文已经不存在了，可那条记录常常还留在保留尾部（遮蔽保留尾部总是留着最后几条），于是它继续当读数。遮蔽砍得动估算、砍不动它，`tokens_after` 就只增不减。

## Decisions

### D1 界取「该装配点之前最后一条 `compaction/summary` 的 `seq`」
校准只认 `seq` 大于它的回合级回复回报；之前没有任何摘要记录时不设界（全部照旧）。**为什么取这个锚点**：它是日志里现成的一条记录，`seq` 单调，replay 从同一份前缀能派生同一个数——不引入进程内状态、不引入新记录类型。**为什么不是「遮蔽范围之外」**：遮蔽范围本身也是那条摘要的 payload，两者等价，但「摘要之后」更直接地说出了这条界的理由（时间，不是位置）。

### D2 不改「被遮蔽的读数不参与校准」那条判据
现状已经排除被遮蔽的那些。问题恰恰是**没被遮蔽**的那条最新回报——它留在尾部，而它描述的正是遮蔽之前那次请求。所以这条界与既有的那条是两条独立的排除，不是一条的加强。

### D3 取舍：读数可能低估真实用量
压缩之后、下一次真实请求带回新回报之前，读数只剩估算。估算偏低时可能多跑一次请求才撞墙——撞到了走既有的那条路（provider 报出的上下文超限塌成同一个溢出结果，请求级压缩上限 1 次，ADR-0019）。**接受**：宁可多撞一次，也不要读数被一个描述过去的数字钉死。钉死的代价已经实测过：一次溢出之后每问必溢出。

### D4 `tokens_after` 的算法不动
`turn_loop.py:678-682` 已经是 `budget_reading(幸存, fold(幸存).messages) + 摘要估算`。读数修对了它自动对。**不加**「遮蔽后强制用估算」这种补丁——那是绕过 D1 的界。

### D5 请求级压缩同样把界往前推
provider 报出超限触发的请求级压缩也写一条 `compaction/summary`，界自然跟着走。不写进规格正文（同一条规则，同一种记录），写进判据：一条 seam ① 的判据观察「请求级压缩之后的读数不含压缩前的回报」。

### D6 判据落点
- **seam ④**（折叠与预算读数）：压缩前的回报不充当压缩后的读数；压缩之后的新回报重新参与校准；同一份前缀两次读数相同（既有那条不许变红）。
- **seam ①**（回合循环的装配点）：遮蔽掉的那段估算大于摘要估算时 `tokens_after < tokens_before`；遮蔽之后读数落回触发线之下、装配照常继续。
- **seam ⑥**（真实子进程）：`[遮蔽] … tokens <前> 降至 <后>` 那一行的两个数满足 `后 < 前`，fixture 带 `usage.input_tokens`（形状照 `.tmp/uat-repro/fixture2.json`；这是 mock 形状不是验收，ADR-0022）。

## Risks & Trade-offs

- **与 `fix-small-window-compaction-dead-zone` 的合并顺序耦合**：本 change 的分支从它的 tip 起，判据照它的压力预算（`W − O`）与那三个数的 detail 写。它的 UAT 那一半没填完，本 change 就排在它后面归档。
- **真实端点验收是必须的**：这条缺陷只在真实端点上出现。mock 复现靠 fixture 带 `usage`——补的是形状，不是验收（ADR-0022）。
- **低估风险**见 D3。
- **replay**：`context/assembled` 的 payload 里记着的读数必须与新算法一致，否则 replay 开始报 `REPLAY_MISMATCH`。既有判据「溢出收尾的日志可被重放」要在新算法下重跑一遍。

## 不做的事（记账）

人的裁决方向，本 change 不做、也不承诺下一个做：**精细的 token 预算管理**——提前看当前表层是否即将立刻满，提前预警并提前压缩，并照 DSH 的做法（target pressure 与 headroom 那套）再做决策。本 change 只把「遮蔽之后读数降得下来」这一件事修对，它是任何提前预警的前置条件：读数降不下来的话，预警永远在报警。落字进 ADR-0029 的 Consequences。**不往 `docs/adr/0002-deferred-refactors.md` 追加**：`fix-small-window-compaction-dead-zone` 与 `add-key-driven-default-provider` 都已经往那份追加过，四条分支都往同一份追加只是给合并添噪音——这一条在合并那一步由人裁决要不要一起落进去。

## Open questions

- 界要不要也排除「同一次装配里越线触发压缩、压缩之后才写出的那条 `model/response`」？**不排**——它描述的正是压缩之后的那次请求，正是该用的读数。
- 要不要给「压缩后估算偏低」加一条下限（例如不低于摘要估算）？不加：没有证据支持，且是最简实现该拒绝的那种补丁。
